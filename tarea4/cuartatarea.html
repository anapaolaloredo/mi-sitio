Reporte 4: Arquitectura Cloud con Prompt Engineering y agentes de IA

Descripción del problema

Una institución financiera desea desarrollar una nueva aplicación de banca móvil bajo una estrategia de nube híbrida: parte de la infraestructura (core bancario, base de datos transaccional, HSM) debe permanecer on-premises por razones regulatorias y de control, mientras que los componentes de cara al usuario (API Gateway, autenticación, microservicios, funciones serverless) se benefician de ejecutarse en la nube por su elasticidad y velocidad de despliegue. El reto es diseñar, prototipar y evaluar críticamente esa arquitectura, en vez de aceptar la primera propuesta generada por IA.

Herramienta de IA utilizada

Claude (Anthropic), vía chat con herramientas de código, búsqueda web y generación de diagramas.

Entorno

Node.js / Express para el prototipo de backend; contenedores vía docker-compose.

Prompt inicial

"Actúa como arquitecto de soluciones Cloud. Diseña una arquitectura para una aplicación de banca móvil utilizando una estrategia de nube híbrida. La solución deberá incluir aplicación móvil, API Gateway, servicios backend, autenticación, bases de datos, almacenamiento, funciones serverless/FaaS, monitoreo y mecanismos de seguridad. Identifica qué componentes deberían permanecer on-premises y cuáles deberían ejecutarse en la nube, justificando cada decisión. Propón una arquitectura escalable, tolerante a fallos y altamente disponible. Genera un diagrama de arquitectura y desarrolla un prototipo básico del backend. Explica cada componente y las decisiones arquitectónicas realizadas."
Resultado: diagrama con frontera cloud/on-premises, justificación tabular de cada componente, prototipo de backend en Node.js (API Gateway, Auth, microservicios de cuentas y transacciones, función serverless de notificación, mock del core bancario on-premises) y documento de arquitectura (ARQUITECTURA.md) con secciones de HA, seguridad y monitoreo.

Prompts de mejora (Prompt Engineering)

No se aceptó la primera respuesta como definitiva. Se aplicaron 5 iteraciones dirigidas a aspectos específicos:

Prompt 2 — Escalabilidad
"Refuta si es completamente escalable o si hay mejoras que se pueden hacer."
Se identificó que la capa cloud escala horizontalmente sin problema, pero el core bancario on-premises y el enlace VPN/Direct Connect son un techo duro de throughput. Se detectaron 7 gaps concretos: sin cache de lecturas, sin cola de mensajes (SQS/Kafka), Auth como punto único de fallo por validar token en cada request, sin circuit breaker/timeouts, estado en memoria (no persistente), rate limiting no distribuido, e Idempotency-Key generado pero no usado para deduplicar.
Prompt 3 — Seguridad y superficie de ataque
"¿Cómo ayuda la seguridad? ¿Hay rutas (endpoints expuestos)?"
Se listaron todas las rutas del sistema (públicas, internas y on-premises) y se evaluó qué protege cada mecanismo (helmet, rate limiting, JWT corto + MFA, filtro por canal). Se identificaron 6 huecos reales: el header "canal VPN" es falsificable (no reemplaza mTLS con certificados), los microservicios internos no tienen autenticación entre sí, la capa de cache no tiene control de acceso, no hay TLS interno, hay un secreto JWT hardcodeado como fallback, y no hay validación/ sanitización de inputs.
Prompt 4 — Comparación con banca real y contexto financiero
"Compara y analiza con otras bancas móviles. ¿Consideraste adecuadamente el contexto financiero?"
Investigación con fuentes actuales (Nubank, patrón Backend-for-Frontend, OAuth2+PKCE, mTLS cliente, cores cloud-native modernos, requisitos de subcontratación de la CNBV). Conclusión: el contexto financiero regulatorio no se había considerado a fondo — faltaba el patrón BFF, OAuth2 con PKCE, motor de fraude/AML, ledger con doble entrada e idempotencia real, trazabilidad (audit trail inmutable exigido por CNBV) y el contrato auditable con el proveedor cloud que exige la regulación mexicana de outsourcing tecnológico.
Prompt 5 — Reducir puntos únicos de falla (implementación)
"¿Estás contemplando el flujo Usuario → App móvil → Servicios Cloud → Backend → Datos → Sistemas on-premises? Si por favor, agrégalo."
Se rediseñó el diagrama para incluir explícitamente una capa de Datos en cloud (cache de saldos tipo Redis, TTL 30s) entre el Backend y los sistemas on-premises. Se implementó en código: services/datacache con patrón read-through (lecturas) e invalidación post-escritura (para no servir saldo obsoleto), reduciendo la carga sobre el core en cada consulta.
Prompt 6 — Observabilidad y recuperación ante desastres
"Incorpora observabilidad real y un plan de recuperación ante desastres."
Se propuso: métricas por servicio (p50/p95/p99, error rate, saturación) exportadas a CloudWatch/ Prometheus, alertas específicas sobre la latencia del enlace VPN/Direct Connect, DR con RTO/RPO definidos (capa cloud stateless reconstruible vía IaC; el core necesita réplica en segundo datacenter), y degradación controlada (servir saldo cacheado con bandera stale: true en vez de colgarse si el core no responde).

Primera arquitectura (versión inicial)

Flujo colapsado: Backend hablaba directo con on-premises, sin capa de Datos intermedia en cloud.

Arquitectura final

Flujo completo: Usuario → App móvil → Servicios cloud → Backend → Datos (cache cloud) → Sistemas on-premises.

Código generado y mejorado

Prototipo completo en Node.js/Express: gateway (proxy + auth + rate limit + logging), services/auth (JWT + MFA simulado), services/accounts y services/transactions (microservicios), services/datacache (capa de Datos, read-through), serverless/notifyFunction.js (handler estilo Lambda) y onprem-mock/core-bancario.js (simulación del core, protegido con validación de canal).

Ejemplo — capa de Datos con patrón read-through (accounts)

app.get('/cuentas/:id/saldo', async (req, res) => {
  // 1) Intenta la capa de Datos (cloud) primero
  const cacheResp = await fetch(`${DATA_CACHE_URL}/cache/saldo/${req.params.id}`);
  if (cacheResp.ok) {
    const cached = await cacheResp.json();
    if (cached.hit) return res.json({ ...cached.data, source: 'cache' });
  }
  // 2) Cache miss: va al core on-premises (fuente de verdad)
  const resp = await fetch(`${CORE_BANCARIO_URL}/cuentas/${req.params.id}/saldo`, {
    headers: { 'X-Internal-Channel': 'vpn-direct-connect' }
  });
  const data = await resp.json();
  // 3) Rellena la cache para próximas lecturas
  fetch(`${DATA_CACHE_URL}/cache/saldo/${req.params.id}`, {
    method: 'PUT', headers: {'Content-Type':'application/json'}, body: JSON.stringify(data)
  }).catch(() => {});
  res.json({ ...data, source: 'core' });
});

Ejemplo — middleware de canal privado (core on-premises)

app.use((req, res, next) => {
  const canal = req.header('X-Internal-Channel');
  if (canal !== 'vpn-direct-connect') {
    return res.status(403).json({ error: 'Acceso solo permitido vía canal privado' });
  }
  next();
});

Reflexión individual

Prompt Engineering: la solución cambió notablemente entre la primera respuesta y la final. El primer prompt (amplio, con muchos requisitos a la vez) produjo una arquitectura correcta en forma pero superficial en fondo: cumplía el checklist visualmente, pero no resistía preguntas puntuales. Cada prompt de mejora que apuntó a un aspecto específico (escalabilidad, seguridad, comparación con el mundo real) sacó a la luz huecos que el prompt genérico no forzaba a resolver. Esto confirma que prompts amplios generan respuestas amplias pero poco profundas; prompts dirigidos a un ángulo concreto fuerzan un análisis más honesto.

Arquitectura: la primera propuesta no era adecuada para producción, aunque sí era un buen punto de partida pedagógico. Colapsaba "Backend" y "Datos" en un solo salto, lo cual simplificaba de más el flujo real que pide el ejercicio.

Errores: sí se detectaron omisiones relevantes: falta de cache/capa de datos, falta de cola de mensajes, Auth como punto único de fallo, y control de acceso ausente entre microservicios internos. Ninguna era obvia a simple vista; salieron al cuestionar la arquitectura activamente.

Seguridad y contexto financiero: no, la IA no consideró adecuadamente el contexto financiero en la primera pasada. Trató el problema como una arquitectura cloud genérica con "seguridad estándar" (JWT, MFA, rate limiting), sin incorporar los requisitos que sí aplican a una banca real: regulación de outsourcing/nube de la CNBV, motor de fraude, doble entrada contable, ledger inmutable y auditoría regulatoria. Esto solo emergió al preguntar explícitamente por el contexto financiero y comparar con bancos/neobancos reales.

Código: sí, el código generado es comprensible en su totalidad — es un prototipo deliberadamente simple (Express, sin frameworks pesados) para que cada decisión (dónde se valida el canal, dónde se invalida la cache, cómo se propaga el trace-id) sea rastreable línea por línea.

Validación: las recomendaciones se verificaron con dos mecanismos: (1) ejecución real del prototipo vía curl, lo que expuso un error práctico (token literal <token> en vez del valor real) que no habría aparecido solo leyendo el código; y (2) búsqueda web de fuentes actuales sobre arquitecturas de banca real (Nubank, patrones BFF, requisitos CNBV) para contrastar el diseño propuesto contra la industria, en vez de aceptar la autoevaluación de la propia IA.

Rol del ITC: para validar una arquitectura generada por IA se necesita conocer, como mínimo: patrones de arquitectura distribuida (microservicios, colas, cache), fundamentos de redes (VPN, mTLS, segmentación), seguridad de aplicaciones (OWASP, gestión de secretos, control de acceso), y el marco regulatorio del dominio (en este caso, banca/fintech en México). Sin eso, es imposible saber qué preguntar.

IA vs. ingeniero: la IA puede delegarse la generación de boilerplate, la exploración de alternativas y la detección sistemática de patrones conocidos (esto se vio en las críticas de escalabilidad y seguridad). Debe permanecer bajo responsabilidad humana: la decisión regulatoria de qué dato puede salir del perímetro on-premises, la aceptación de riesgo residual, y la validación empírica (correr el código, no solo leerlo).

Conclusión de la reflexión: no, una persona sin bases sólidas de arquitectura, redes y seguridad no podría evaluar correctamente esta solución usando solo IA. La IA respondió con seguridad y coherencia interna incluso cuando la primera versión tenía huecos importantes; sin criterio propio para cuestionarla con las preguntas correctas, esos huecos habrían pasado como "arquitectura completa".

Conclusiones

El ejercicio demostró que una IA generativa produce con facilidad una arquitectura visualmente completa y técnicamente razonable en la primera pasada, pero que su profundidad depende directamente de qué tan específicas y críticas sean las preguntas de seguimiento. El valor del ingeniero no está en generar el primer diagrama, sino en saber qué preguntarle después: dónde se rompe la escalabilidad, qué rutas quedan expuestas, y si el contexto regulatorio del dominio (banca, en este caso) realmente se respetó. La arquitectura final es más honesta que la inicial no porque la IA "supiera más" al final, sino porque se le exigió más.
